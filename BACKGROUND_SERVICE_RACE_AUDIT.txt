Identified Risks:
==============================================================

RISK #1: Device List Cache Corruption
File: Likely in SyncScheduleRepository or device cache
Scenario:
1. UpdateCheckService fires at T=0
2. Fetches device list for version check: lock acquired
3. DeviceHealthSyncService fires at T=5ms
4. Attempts to refresh device health: WAITS for lock
5. Both services read/modify device list simultaneously

Symptoms if race exists:
- Device count mismatch
- Missing devices after sync
- Duplicate device entries
- Null reference exceptions accessing device properties

RISK #2: Session State Corruption
File: LiveViewIdleTimeoutService
Scenario:
1. Active session list: [Session A, Session B, Session C]
2. Timer fires at T=0: Iterates list to find idle sessions
3. Timer fires at T=100ms: Another instance adds Session D
4. First iteration reads stale list (3 items)
5. Second iteration writes new list (4 items)
6. Thread A sees 3, Thread B sees 4 - inconsistent state

Symptoms:
- Sessions not properly closed
- Session list grows indefinitely
- Memory leak (sessions never garbage collected)

RISK #3: Health Status Data Loss
File: DeviceHealthSyncService + Device entity
Scenario:
1. DeviceHealthSyncService fetches fresh health data
2. Updates Device.HealthStatus field
3. CameraBitrateCalibrationService reads HealthStatus
4. Modifies Device.BitrateSettings (same entity)
5. Both write back - one overwrites the other

Symptoms:
- Health status data lost
- Bitrate settings reverted
- Inconsistent state between services

Example: Session List Race
```csharp
// UNSAFE (without lock):
public class LiveViewIdleTimeoutService
{
    private List<Session> _activeSessions = new();

    public void AddSession(Session session)
    {
        // RACE: Timer may fire and iterate here
        _activeSessions.Add(session);
    }

    public void CheckIdleSessions()
    {
        // RACE: Another thread adds to list while iterating
        foreach (var session in _activeSessions)
        {
            if (session.IsIdle)
            {
                _activeSessions.Remove(session); // Modifying during iteration!
            }
        }
    }
}

// SAFE (with lock or ConcurrentCollection):
public class LiveViewIdleTimeoutService
{
    private readonly List<Session> _activeSessions = new();

    public void AddSession(Session session)
    {
        lock (_activeSessions)
        {
            _activeSessions.Add(session);
        }
    }

    public void CheckIdleSessions()
    {
        lock (_activeSessions)
        {
            // Iterate on snapshot
            var sessions = _activeSessions.ToList();
            foreach (var session in sessions)
            {
                if (session.IsIdle)
                {
                    _activeSessions.Remove(session); // Now safe
                }
            }
        }
    }
}

// ALTERNATIVE (ConcurrentBag):
private readonly ConcurrentBag<Session> _activeSessions = new();
```

Test Scenario Design:
==============================================================

Test Name: BackgroundServices_NoRaceConditions_WhenMultipleServicesFireSimultaneously()

Test Approach:
1. Create test instance of each service
2. Inject test doubles for dependencies
3. Manually trigger multiple timers simultaneously
4. Verify no data corruption
5. Repeat 100 times to increase chance of race detection

Pseudo-code:
```csharp
[Fact]
public async Task BackgroundServices_NoRaceConditions_WhenMultipleServicesFireSimultaneously()
{
    // Setup
    var deviceCache = new TestDeviceCache();
    var sessionList = new TestSessionList();
    var healthCache = new TestHealthCache();

    var updateCheckService = new UpdateCheckService(deviceCache);
    var healthSyncService = new DeviceHealthSyncService(deviceCache, healthCache);
    var liveViewService = new LiveViewIdleTimeoutService(sessionList);

    // Stress test: Fire all services simultaneously 100 times
    for (int iteration = 0; iteration < 100; iteration++)
    {
        var tasks = new[]
        {
            updateCheckService.CheckForUpdatesAsync(CancellationToken.None),
            healthSyncService.SyncDeviceHealthAsync(CancellationToken.None),
            liveViewService.CloseIdleSessionsAsync(CancellationToken.None)
        };

        // Fire at same time (as much as threads allow)
        await Task.WhenAll(tasks);

        // Verify consistency
        Assert.True(deviceCache.IsConsistent(), $"Device cache corrupted on iteration {iteration}");
        Assert.True(sessionList.IsValid(), $"Session list invalid on iteration {iteration}");
        Assert.True(healthCache.IsConsistent(), $"Health cache corrupted on iteration {iteration}");
    }
}
```

Expected Outcomes:
==============================================================

If NO race conditions exist:
- Test passes all 100 iterations
- Data remains consistent throughout
- No exceptions thrown

If race conditions exist:
- Test fails (usually within first 10 iterations)
- AssertionError: Cache inconsistent
- Possible: ObjectDisposedException, IndexOutOfRangeException, NullReferenceException

Common Race Symptoms:
- First run: Pass (coincidental ordering)
- Second run: Fail (different timing, race manifests)
- Intermittent failures (race condition signal)

Safety Practices for Multi-Threaded Background Services:
==============================================================

DON'T:
- Use List<T> shared across threads (race condition)
- Iterate list while another thread modifies (IndexOutOfRange)
- Read field, modify, write back (read-modify-write race)
- Share DbContext across operations (DbContext not thread-safe)
- Assume startup order (Race with initialization)

DO:
- Use ConcurrentBag, ConcurrentDictionary, ConcurrentQueue
- Use lock for simple/legacy scenarios
- Use ReaderWriterLockSlim for read-heavy scenarios
- Use interlocked operations for primitives (Interlocked.Increment)
- Inject separate DbContext per operation
- Document thread safety assumptions
