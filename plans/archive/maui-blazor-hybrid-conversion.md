## Context

The console TUI app (Spectre.Console, `src/client/VideoForensics`) currently covers ~30 screens of functionality — evidence collection, review/export, forensic analysis reports, jamming detection (MCP-only today, no console UI), device/account management, and configuration — all built on a solid, already-decoupled service layer (`data.common`/`data.core`/`data.database*`, `providers/ring/*`, `client/core`, `client/common`). That service layer needs no redesign; only the presentation layer is being replaced.

The goal is to replace the console app with a **.NET MAUI Blazor Hybrid + Web App** (Microsoft's single-project template): one shared Razor Class Library of pages/components, hosted natively on Windows via MAUI and as a real website via ASP.NET Core Blazor Server — giving Linux/browser access without needing a MAUI build on Linux (MAUI has no Linux desktop target).

The architecture that emerged over this planning session is a proper **client/server split**: the server owns the database *and* the media files, and other devices (a Windows MAUI install, a browser) are paired clients that authenticate to its API — with careful attention to security since this handles sensitive DV-safety evidence and the server may eventually be reachable from the internet.

Real gaps folded into this plan along the way:
1. **RSSI telemetry is too sparse** for jamming detection (only captured once per video-download batch) — needs a proper periodic background sync, battery-aware where the host can know about battery state.
2. **Auth/session state is single-slot** (`ISessionProvider` holds exactly one `Session`) — the Web host needs genuine concurrent multi-Ring-account support.
3. **The database and media files become server-owned**, with paired clients (MAUI, browsers) authenticating via a QR-code pairing ceremony that provisions a passkey, and the server exposing itself at one of three access tiers (Local/Network/Internet-via-tunnel).

The console app itself is not deleted — it moves to `archive/` once the new app reaches parity, per this repo's existing (if previously unused) `archive/`-directory convention noted in `CLAUDE.md`.

**Four important layers stay conceptually separate throughout this plan:**
- **Ring account auth** (existing) — OAuth-based, per Ring account, governs what Ring data can be fetched. Unchanged except for the multi-account session keying in §2.
- **Client/device pairing auth** (new, §5.1) — governs which *physical devices* (a MAUI install, a browser) are allowed to talk to the server's API at all.
- **Operator identity** (new, §5.1/§5.11) — governs *which specific person* is using a paired device, for legal attribution. Distinct from the existing Ring-scoped `User` entity (which represents the Ring account holder, keyed by `ProviderUserKey`) — a new `Operator` entity represents a local person operating this VideoForensics installation.
- **Role-based permissions** (new, §5.10) — governs what an already-paired, already-identified operator is allowed to *do*: view only, annotate, manage evidence, or administer the server itself.

## 1. Shared hosting consolidation (`VideoForensics.Hosting`)

Both existing entry points (`VideoForensics/Program.cs`, `VideoForensics.Mcp/Program.cs`) currently duplicate the same ~40-line DI registration block. Extract it once:

**Only the server pulls new media from any provider — clients never talk to a provider directly.** This repo already treats providers as pluggable behind `VideoForensics.Providers.Common.Contracts` (`IProviderAuthService`/`IDeviceDiscoveryService`/`IMediaDownloadService`/`IEventAndConfigService`/`IVideoProvider`, per `CLAUDE.md`'s "Adding a New Provider" convention) — Ring is fully implemented today, Wyze has an existing scaffold (`providers/wyze/*`). Nothing in this plan is Ring-specific by design; the server registers **every provider that's implemented and configured**, the same way "Manage Accounts → Add Account" already lets you pick Ring or Wyze. The registration extraction splits into two tiers, not one:

```csharp
// Server-only: every implemented provider's four services (auth, discovery, download,
// event/config), registered per-provider the same way "Adding a New Provider" already
// prescribes — plus the actual download/import orchestration (IVideoDownloadService).
// Called ONLY by VideoForensics.WebApp. Adding a new provider later (per CLAUDE.md's existing
// convention) is a registration addition here, not a rewrite of this method's shape.
public static IServiceCollection AddVideoForensicsServerCore(this IServiceCollection services) { ... }

// Shared by every host, server or client: the data layer only (repositories, EF Core). The
// server uses this for its real DB; MAUI uses it for its local offline-review cache (§4).
public static IServiceCollection AddVideoForensicsDataLayer(this IServiceCollection services) { ... }

// Client-only: HTTP-backed implementations of the same download-orchestration and repository
// shapes, calling the server's API instead of touching Ring or a local DB (§4, §6). Called by
// VideoForensics.MauiApp.
public static IServiceCollection AddVideoForensicsClientApi(this IServiceCollection services, Uri serverAddress) { ... }

public static Task InitializeVideoForensicsDataAsync(IServiceProvider sp, ILogger logger, CancellationToken ct) { ... }
```

`AddVideoForensicsServerCore()` + `AddVideoForensicsDataLayer()` together wrap the exact registrations already in `VideoForensics.Mcp/Program.cs:100-163` (today: Ring's four provider services; Wyze's added the same way once its scaffold is complete — see `CLAUDE.md`'s "Adding a New Provider" steps — plus `AddVideoForensicsSqlite/Database/DataCore`, orchestrators) and the deferred-init sequence (`DatabaseInitializer.InitializeAsync` → `EventBackfillService.BackfillFromDownloadEventsAsync` → `ConfigurationLoader.LoadAndApplyAsync`) — this is what the console and MCP `Program.cs` refactor to call (both remain direct provider-talking processes, unaffected by the client/server split, which only applies to the new MAUI app). `VideoForensics.WebApp` calls both server-tier methods too, since it *is* the server. `VideoForensics.MauiApp` calls only `AddVideoForensicsDataLayer()` (for its local cache) + `AddVideoForensicsClientApi()` — it never registers any provider's services and has no code path capable of calling a provider's API directly, by construction, regardless of how many providers the server supports.

Refactoring the console and MCP `Program.cs` to use the server-tier methods is a low-risk, behavior-preserving PR that proves the extraction before any new UI depends on it, and should land first (M1).

## 2. Multi-user session model (Ring account layer)

Current `ISessionProvider` (`src/providers/ring/provider/Services/ISessionProvider.cs`) is a single mutable field — fine for the console/MCP (one operator, one process) but wrong for a Web host with concurrent browser circuits potentially on different Ring accounts.

`ICredentialStore` is already **path-parameterized** (`Load(string path)`/`Save(string path, ...)`) — the storage layer isn't the bottleneck. `IProviderAuthService.RestoreFromSavedCredentialsAsync(Guid? providerAccountId, CancellationToken)` **already exists** (`RingAuthService.cs:234`) — the account-scoped restore path is already there. `ISessionProvider` is the actual gap.

**Change**: key `ISessionProvider` by `providerAccountId` instead of being a single slot:

```csharp
public interface ISessionProvider
{
    Session? GetSession(Guid providerAccountId);
    void SetSession(Guid providerAccountId, Session session);
    void ClearSession(Guid providerAccountId);

    // Back-compat convenience for single-tenant hosts (console/MCP/MAUI): operates on
    // whichever account was set most recently, so existing call sites in Client.Core
    // (VideoDownloadServiceAdapter, EvidenceValidationOrchestrator, etc.) need no changes.
    Session? GetSession();
    void SetSession(Session session);
    void ClearSession();
}
```

Backed by a `ConcurrentDictionary<Guid, Session>` plus a "last set" key for the parameterless overloads. This is an additive interface change (new overloads, old ones keep working) — no ripple into Client.Core orchestrators.

New **scoped** service `ICurrentAccountContext` (registered per-circuit in the Web host, effectively singleton-shaped in MAUI) holds "which Ring account is *this* browser tab/session currently acting as" — settable from the Manage Accounts screen, read by every device/date-range picker component.

## 3. RSSI/health background sync (all hosts, config-gated, battery-aware, per-provider)

Health/signal telemetry isn't guaranteed to work the same way across providers (Ring exposes it via `GET /clients_api/ring_devices`; Wyze's equivalent, if any, is unknown/unimplemented today) — so this is designed as an **optional per-provider capability**, not a Ring-only service, matching §1's "every implemented provider, registered the same way" stance.

1. **Extract `FindDeviceHealth`** out of `RingMediaDownloadService.cs` (currently `internal static`, line ~1120) into a new public static `DeviceHealthMatcher` class in the same project (`src/providers/ring/provider/Services/DeviceHealthMatcher.cs`) — pure move, no behavior change, update `CaptureDeviceHealthSnapshotAsync` and the existing `RingMediaDownloadServiceTests` `FindDeviceHealth_*` cases to reference it. Lands as a standalone PR before anything else (M1 warm-up).

2. **New optional capability interface** `IProviderHealthSource { Task<IReadOnlyList<DeviceHealthReading>> FetchHealthAsync(CancellationToken ct); }` in `VideoForensics.Providers.Common.Contracts` — a provider implements this only if it can supply health/signal data. `RingHealthSource` (wrapping the existing `session.GetRingDevices()` + `DeviceHealthMatcher` logic) is the first implementation; Wyze gets one later if/when its API supports it, following the same contract.

3. **New `DeviceHealthSyncService : BackgroundService`** (provider-agnostic name, deliberately not `RingDeviceHealthSyncService`) in `VideoForensics.Hosting/BackgroundServices/`. `ExecuteAsync` runs a `PeriodicTimer` loop: skip the tick if `IForensicsConfiguration.EnableHealthSync` is false (new setting, default on, Configuration screen toggle); otherwise iterate every registered `IProviderHealthSource` (just Ring today, more later, none of this code changes when a second one is added), persist each result via `IVideoForensicsDataClient.RecordDeviceHealthSnapshotAsync` (same call `CaptureDeviceHealthSnapshotAsync` already makes — one persistence entrypoint, not two). Entire tick body wrapped in try/catch per provider (a `BackgroundService` that throws stops permanently under ASP.NET Core hosting, and one provider's failure shouldn't block another's).

4. **Battery awareness** — genuinely low effort: define `IBatteryStatusProvider { BatteryStatus GetStatus(); }` (`OnAcPower | OnBattery | Unknown`) in `VideoForensics.Hosting`. Default no-op implementation (`AlwaysOnAcPower`) registered by console/MCP/Web hosts. MAUI-only implementation `MauiBatteryStatusProvider` wraps `Microsoft.Maui.Devices.Battery` (built into the MAUI SDK, no extra package). `DeviceHealthSyncService` multiplies its interval (e.g. ×3) when on battery/energy-saver rather than stopping entirely. (This implementation ends up server-only per point 5 below, but the abstraction stays host-agnostic since a future mobile MAUI target would want it too, for whatever *does* legitimately run there.)

5. **Registered in server-tier hosts only — console, MCP, and `VideoForensics.WebApp` — never MAUI.** `IProviderHealthSource.FetchHealthAsync()` calls a provider's API directly (for Ring, `session.GetRingDevices()`), which would directly violate §1's "no client host registers any provider's services or calls a provider's API, by construction" rule if MAUI ran it too. MAUI's local cache instead picks up updated health snapshots the same way it picks up any other server-produced data — through the normal client read-sync (§4/M7), not an independent Ring poll. `AddVideoForensicsHealthSync()` is therefore called from `AddVideoForensicsServerCore()` (§1), not from MAUI's `Program.cs`.

**Known limitation, stated rather than silently accepted**: console, MCP, and `VideoForensics.WebApp` can each independently run this same background sync against the same Ring account if more than one happens to be running at once (e.g. a user still has the console app open alongside the new Web server) — each is a legitimate standalone "server-tier" process per §1, so nothing currently coordinates between them, and redundant polling could contribute to hitting Ring's own rate limits. Not fixed in this plan; worth revisiting once the console app is archived (M4) reduces how often multiple server-tier processes actually run concurrently.

## 4. Server-owned database and media storage

`VideoForensics.WebApp` becomes the **only** process that opens the SQLite DB directly *and* the only place downloaded video/snapshot files live. No engine change needed (same SQLite file), but ownership centralizes.

Add a Minimal API surface (`VideoForensics.WebApp/Api/*Endpoints.cs`) wrapping the existing repository contracts one-for-one (`/api/devices`, `/api/media-items`, `/api/integrity-records`, `/api/jamming/*`, etc.) — mechanical, since every data access already goes through a `Contracts/` interface per `CLAUDE.md`'s existing convention. Media files get their own streaming endpoints (`GET /api/media/{id}/content`) rather than being embedded in JSON responses.

**Built against the `IMediaStorageProvider` abstraction from the start (M5), even though only one implementation ships then.** The media endpoints write/read through `IMediaStorageProvider` (`SaveAsync`/`OpenReadStreamAsync`/`DeleteAsync`), not directly against local-disk file I/O — M5 registers only `LocalDiskMediaStorageProvider` (today's behavior), and the API surface itself is written generically enough that any authenticated caller (a MAUI client *or*, later, a replica server per §4.3) uses the same endpoints. This means M8 (§4.2's `SecureNetworkMediaStorageProvider`, §4.3's server-to-server sync) is purely **additive** — a second `IMediaStorageProvider` implementation plus a new client of the existing API surface — not a refactor of M5/M6's work. Concretely, this is the one piece of §4.2/§4.3 that *is* being built now, not just designed now: the seam, not the future implementations behind it.

**Downloads/imports are server-executed actions, requested by API.** A client (MAUI, or the Web app's own UI) never invokes `IVideoDownloadService` locally — it calls `POST /api/downloads/videos` or `POST /api/downloads/snapshots` (request body: device, date range), and the *server* runs the actual `VideoDownloadServiceAdapter`/Ring-download pipeline, since that's the only process with Ring provider services registered (§1). Progress/status is likewise served from the server via `GET /api/downloads/status` — see §6, which the Web app's own Blazor pages call through the same in-process implementation of that endpoint's underlying method (not a real HTTP round-trip to itself), keeping one code path for "how progress is obtained" regardless of host.

MAUI client: keeps a local SQLite cache purely for **offline review** (browsing previously-synced evidence/reports without a network connection) and gets `Remote*Repository : IXxxRepository` implementations (HTTP client) for the same read-oriented contracts, plus on-demand media streaming/caching rather than bulk-copying the whole library. It has no local write path for new evidence — new media only ever originates server-side, from a download the server itself executed. The **offline sync engine** (§4, reconciling the local read-cache with the server, media caching strategy) is real, separate design work — scoped as its own milestone (M7) with a focused follow-up plan once the server API (M6) is stable, not fully speccing conflict resolution here. It's a simpler problem than originally scoped, precisely because the client no longer originates download data — sync is now pull-only refresh of a read cache, not two-way reconciliation of independently-created evidence.

### 4.1 Database encryption at rest (media files explicitly excluded, with a warning)

The **SQLite database file itself gets encrypted at rest** — via SQLCipher (`SQLitePCLRaw.bundle_e_sqlcipher` + EF Core's Sqlite provider, a well-established combination) rather than relying on OS-level disk encryption, so the DB is protected regardless of whether the host machine has BitLocker/FileVault enabled. The encryption key is managed through the app's **existing** key-storage abstraction — the console app already has a "Key Storage Configuration" screen (Auto/TPM/DPAPI/FileBased provider selection) and `ICredentialEncryptionProvider`/`CredentialEncryptionProvider` pattern used for credential encryption today; DB-at-rest encryption reuses that same provider selection rather than inventing a second key-management mechanism.

**Bootstrap circularity, caught in review and resolved**: the key-storage-provider *selection* (which mechanism to use) is normally an app setting, and app settings normally live *in* the database via `IAppSettingRepository` — which is exactly the DB this key is meant to unlock. That's circular. Resolved by keeping the DB-encryption key (and which provider produced it) **outside** the encrypted DB entirely, in the same small local bootstrap file/OS-credential-store (DPAPI/TPM-backed) the app already uses for Ring credentials before any DB access happens today (`ICredentialStore`'s file-based, path-parameterized storage, §2) — read once at process startup, before `DbContextFactory` ever opens the file. Everything *else* about key-storage configuration (which provider is active, UI toggles) can still live in the encrypted DB as a normal setting; only the DB's own key material has to sit outside it.

**All new secrets this plan introduces route through this same abstraction, not new plaintext settings**: SMTP credentials (§5.6), notification-provider API keys (§5.6), Cloudflare Tunnel credentials (§5.3), and network-storage share credentials (§4.2) all go through `ICredentialEncryptionProvider`/the key-storage-provider mechanism — stated once here rather than repeated in each of those subsections, since it's one rule, not four separate decisions.

**Media files (downloaded video/snapshot content) are explicitly NOT encrypted at rest by default in this plan** — encrypting potentially large video files adds real complexity (streaming encrypt/decrypt, performance overhead) that wasn't asked for and would meaningfully expand scope. Instead: a persistent, clearly-worded warning is surfaced (on the server's storage/security settings screen, and as a one-time acknowledgment during first-run server setup) stating that media files are stored in plain form on disk by default, and that full-disk encryption or physical security of the server machine is the owner's responsibility for that data unless secure network storage (§4.2) is configured. This is a deliberate, stated scope boundary for the default path, not an oversight.

### 4.2 [Future work, planned now] Secure network media storage

An optional alternative to local-disk media storage: point the server at a network location instead. The `IMediaStorageProvider` abstraction this needs is **already built in M5** (see §4) with only `LocalDiskMediaStorageProvider` behind it; M8 adds `SecureNetworkMediaStorageProvider` as a second implementation, selected via a storage-location setting — no changes needed to the API surface or M5's endpoints.

**Cross-platform by design, without reimplementing SMB/NFS clients**: rather than the app speaking the SMB/NFS wire protocol itself (a large, platform-specific undertaking that would need separate Windows/Linux implementations), the OS does the mounting — the admin mounts their network share/NAS at the OS level (a drive letter on Windows, a mount point on Linux via `cifs-utils`/NFS), and `SecureNetworkMediaStorageProvider` just writes to that configured path like local storage, plus: (a) a startup/periodic **mount-health check** (the configured path is actually a live mount, not a dangling reference to an unmounted share — fail loudly rather than silently writing to the wrong place), and (b) an **application-level encryption wrapper** around each file written there — this is the natural place to actually deliver at-rest media encryption for users who opt into network storage specifically, without revisiting §4.1's default-path scope boundary. "Secure" here means: encrypted transport to the share (SMB3 with encryption enabled, or a TLS-backed protocol like SFTP/WebDAV over HTTPS — plain unencrypted SMB1/NFSv3 explicitly discouraged in the setup UI) plus this application-level file encryption, keyed through the same key-storage-provider abstraction as §4.1.

### 4.3 [Future work, planned now] Server-to-server sync (multi-instance, master/replica)

Lets the owner run `VideoForensics.WebApp` on more than one machine (e.g. a home desktop and a laptop) and have them stay in sync, rather than being fully independent islands.

- **Master/replica, not peer-to-peer**: exactly one server instance is designated **master** (authoritative) via a setting; every other instance is a **replica**. This mirrors the same "designate an authority, others defer" conflict policy already established for the client offline-sync engine (§4/M7) — deliberately the *same* policy, not a second design, for consistency and so the M7 sync engine can be built generically enough from the start to serve both "MAUI client ↔ server" and "replica server ↔ master server" without being rebuilt for M8.
- **Only the master actively pulls new media from providers** — replicas never call Ring (or any provider) directly themselves, preserving §1's "only the server pulls new media" rule even in a multi-server topology (the master *is* "the server," singular, in that rule; a replica is more like a full-featured read-mostly mirror that could later be promoted to master).
- **Reuses the pairing mechanism, not a new protocol**: from the master's point of view, a replica server is authenticated the same way a MAUI client is — the same QR-pairing/passkey ceremony (§5.1) — rather than inventing a separate server-to-server trust mechanism. A replica's sync traffic rides the same Minimal API surface (§4) as client sync.
- **Works identically on Windows and Linux masters/replicas** — the sync protocol is plain HTTPS/API calls (already platform-agnostic ASP.NET Core), so no OS-specific server-to-server code is needed; any mix of Windows/Linux instances can sync with each other.
- Explicitly scoped as **future work planned now, not built now** — this becomes its own milestone (M8, after M7's sync engine exists to build on) with a focused follow-up design once M7 is real, per the same "don't fully design conflict resolution twice in one already-large plan" reasoning as M7 itself.

### 4.4 Legal hold / retention override

The existing Retention Policy setting (`ConfigToolsOrchestrator.SetRetentionDaysAsync`, a global days-count) auto-deletes evidence past that age wherever the retention-cleanup routine runs. Once evidence lives on one shared server backing an active case, a global "delete after N days" policy shouldn't be able to quietly destroy evidence someone's relying on for that case.

New `LegalHold` entity (Id, media-item or device+date-range scope, Reason, CreatedByDeviceId, CreatedAtUtc, ReleasedAtUtc?) behind a new `ILegalHoldRepository`. The retention-cleanup routine checks for an active hold covering an item before deleting it and skips deletion if one exists. "Place under legal hold" / "Release hold" become actions on the **Review Evidence** screen (`/review`), each requiring a stated reason — and, unlike §5.5's *security* audit log, these are logged to the **existing evidence chain-of-custody trail** (`ChainOfCustody`/`ActionLog`), since this is evidence-handling, not server-security activity — keeping the two audit logs' scopes clean and non-overlapping, per the distinction already drawn in §5.5.

## 5. Secure device pairing & remote access

This is the highest-sensitivity part of the plan — the server is now the sole custodian of DV-safety evidence, so client authentication and network exposure need to be right, not just functional.

### 5.1 QR pairing ceremony (Signal-style)

1. On the server (already signed into a Ring account), the owner opens a **"Devices" / "Add Client"** settings screen.
2. Server generates a short-lived (~2 min), single-use, high-entropy pairing token, encodes it plus the server's currently-reachable address into a QR code (e.g. `https://<server-address>/pair?token=<token>`), and displays it.
3. The new client (MAUI app's "Connect to Server" screen, or another browser) scans the QR with its camera, extracts the address + token.
4. Client calls the server's pairing endpoint with the token over **HTTPS** — required even for Local/Network tiers, because WebAuthn/passkeys only work over a secure origin (HTTPS or exact `localhost`). The server needs to generate/manage its own TLS certificate (self-signed, trusted via the pairing ceremony itself — the QR payload can include a certificate fingerprint the client pins on first connect, avoiding a separate CA trust step) for LAN/local reachability; the Internet tier gets real TLS for free from the Cloudflare Tunnel edge. **The pinned fingerprint is checked on every subsequent connection from that device, not just at pairing** — the client stores it alongside the paired-device record and refuses to connect (rather than silently falling back to unpinned trust) if a later connection presents a different certificate; a fingerprint mismatch itself is a `SecurityAuditLogEntry`-worthy event once the client can report it back.
5. Client identifies **who this is for** — select an existing `Operator` (§5.11) or create a new one (display name) — before the credential ceremony runs, so the resulting passkey is bound to a specific person, not just an anonymous device.
6. Server validates the token (unexpired, unused) and starts a **WebAuthn registration ceremony**: issues a challenge, **the client's own platform authenticator creates the passkey on the client's own device** — Windows Hello on the MAUI Windows app, the browser's own WebAuthn API on the Web client — and returns the public key + attestation. Stated explicitly since it's easy to worry about otherwise: **this works identically whether the client is on the Local, Network, or Internet tier** — the authenticator ceremony happens entirely on the *client's* own machine (their own Windows Hello prompt on their own laptop), not the server's, so network distance from the server doesn't change how the passkey gets created. Server stores the public key against a new **paired-identity record** — (Operator, device credential, Role) — tied to the pairing token (not to a specific Ring account — pairing authenticates the *operator+device*, per the layering note in Context).
7. From then on, that operator+device pair authenticates API calls via a normal WebAuthn **authentication ceremony** (challenge/response, signed by the passkey) at sign-in, establishing a session token — carrying both the `OperatorId` and device identity — used for subsequent API calls and for attribution in audit logs (§5.5) and chain-of-custody entries (§4.4).

**Feasibility flag, stated plainly**: browser-based WebAuthn (the Web client) is well-trodden (native `navigator.credentials` support). Native WebAuthn on **MAUI Windows** is less so — Windows exposes it via the native `webauthn.dll` API (Windows 10 1903+, backs Windows Hello), reachable from .NET via P/Invoke, but there's no first-party MAUI wrapper today. Recommend an early spike (start of M6) to prove this out; if native WebAuthn P/Invoke proves too costly short-term, fall back to: the same QR-pairing ceremony issues a long-lived, device-bound API key instead of a passkey, stored via MAUI's built-in `SecureStorage` (backed by Windows Credential Manager) — same pairing UX, weaker-than-passkey but still solid device-bound auth, and upgradable to real passkeys later without redesigning the pairing flow.

### 5.2 Network access tiers

Server settings screen (`/settings/network`) with three explicit tiers:

- **Local** (default on first install) — server only reachable from its own machine (loopback). No pairing of *other* devices is possible until the owner explicitly widens scope.
- **Network** — reachable on the LAN (today's mDNS-discoverable scope: `_videoforensics._tcp.local` advertisement carrying the server's address, so a MAUI install on the same network can find it during pairing without typing an IP).
- **Internet** — additionally exposed via a Cloudflare Tunnel (§5.3).

Each tier is an explicit, deliberate opt-in with a clear on-screen warning of what it means (matches the "local-only by default, DV-safety evidence" decision) — the app never silently widens its own exposure.

### 5.3 Cloudflare Tunnel GUI

A settings screen (`/settings/remote-access`) that:
- Detects whether `cloudflared` is installed; offers to download/install it if not.
- Lets the owner choose a **quick tunnel** (ephemeral `*.trycloudflare.com` URL, no Cloudflare account needed — good for short-term remote access) or a **named tunnel** (persistent URL, requires the owner's own Cloudflare account/domain, walks through `cloudflared tunnel login` + config).
- Starts/stops the `cloudflared` process (as a managed child process) and shows live status/logs in the UI.
- Surfaces the resulting public URL, usable to generate an internet-reachable pairing QR code.

Note stated explicitly in-app: the tunnel only handles network transport — it doesn't replace the pairing/passkey auth in §5.1; an unauthenticated request over the tunnel still can't reach any data, which is *why* internet exposure is acceptable once passkey pairing is in place.

### 5.4 Device revocation

The same **"Devices" screen** (`/settings/devices`) that shows the QR pairing action also lists every currently-paired identity — (Operator, device) per §5.11 — with name/operator, paired date, last-seen date, source IP/tier at last connection, and a **"Revoke"** action per row. Revoking:
- Deletes the stored passkey public key (or fallback SecureStorage-key hash) from the paired-identity record, so any *future* authentication attempt from it fails immediately.
- Invalidates that identity's currently-active session token server-side (not just letting it expire naturally) — the session-token validation on every API call checks the paired-identity record's revocation status, not just the token's own signature/expiry, so a revoked identity is locked out within one request round-trip, not "eventually."
- **Caught in review: also forcibly disconnects any live SignalR connection (§6) for that identity.** Token invalidation alone only blocks *future* discrete HTTP requests — it does nothing to an already-open, persistent SignalR connection, which keeps streaming download progress/notifications until it happens to reconnect on its own. Revocation must explicitly call the hub's connection-management API to terminate that specific connection immediately, not just rely on the next request being rejected.
- Is itself a security-audit-logged event (§5.5).

This is treated as a first-class action symmetric with pairing, not an afterthought — for a DV-safety tool, "an identity that shouldn't have access anymore, doesn't" needs to be immediate and reliable across every channel, live connections included, not just the next HTTP request. (Deactivating an *Operator* entirely, revoking every device they've paired in one action, is the bulk equivalent — §5.11.)

### 5.5 Security audit log

A dedicated log — separate from the existing evidence chain-of-custody audit trail (`ChainOfCustody`/`ActionLog`, which is about *evidence handling*, not server security) — capturing events on the new security surface: `PairingInitiated`, `PairingCompleted`, `PairingRevoked`, `AuthSuccess`, `AuthFailure`, `SessionVerified` (§5.11's per-session re-verification — recorded every time, not just on failure, so there's a positive record of exactly when each Operator's presence was freshly confirmed, not only a record of problems), `NetworkTierChanged`, `TunnelStarted`, `TunnelStopped`, `ProviderRateLimitHit`, `ProviderApiVolumeAnomaly` (§5.12 — the "Ring API budget under attack" signals). New entity `SecurityAuditLogEntry` (Id, TimestampUtc, EventType, **OperatorId?**, DeviceId?, SourceIp?, Details) behind a new `ISecurityAuditLogRepository` (same `Contracts/` convention as everything else), written to by the pairing endpoints, the auth middleware (including every session-start verification, not just failures), the network-tier change handler, the Cloudflare Tunnel start/stop actions, and `IProviderApiBudgetGuard`/`IsRateLimitError` (§5.12). Read-only screen at `/settings/security-log`, filterable by Operator — this is what makes §5.11's "who did what, when, verified how" story actually queryable rather than just theoretically true.

### 5.6 Urgent security notifications

The same event stream that feeds §5.5's log also drives real-time alerts — a log entry nobody checks doesn't help if someone's actively trying to get in. Each `SecurityAuditLogEntry` event type gets an `IsUrgent` classification (e.g. `AuthFailure` past a small threshold, any `PairingCompleted`, `NetworkTierChanged` to Internet, `PairingRevoked` — vs. routine `TunnelStopped` likely isn't urgent), configurable per event type on a new `/settings/notifications` screen.

Channels are **pluggable providers** behind a common contract — `INotificationProvider { Task SendAsync(NotificationEvent evt, CancellationToken ct); }` in `VideoForensics.Providers.Common.Contracts` (same "interfaces in `Contracts/`, swappable implementations" convention `CLAUDE.md` already establishes for camera providers) — rather than a fixed hardcoded list, so free push services and SMS gateways can be added as optional, user-enabled providers without redesigning this layer:
- **Email** (baseline, ships enabled once SMTP is configured) — reaches the owner regardless of whether any client app is open; the one channel that actually guarantees delivery for a self-hosted app with no cloud backend.
- **Web Push** (browser client) — VAPID key pair generated once by the server, browser subscribes via a service worker + notification permission prompt, server pushes via the Web Push protocol (e.g. the `WebPush` NuGet package). Works even with the browser tab closed, as long as the browser itself is running.
- **MAUI local/toast notifications** — while the MAUI app process is alive (foreground or backgrounded), it surfaces urgent events pushed to it over the same SignalR connection used for download progress (§6 — one real-time channel serving both concerns, not two, per the inefficiency caught in review below) as OS toast notifications. Stated plainly: this **cannot** wake a fully-closed MAUI app — true push-to-closed-app needs a platform push relay (Windows Notification Service), out of scope here; email covers that gap.
- **Optional providers** (off by default, user opts in per-provider with their own API key/config): free push-relay services (e.g. `ntfy.sh`, Pushover) and SMS gateways (e.g. a free-tier Twilio number, carrier email-to-SMS) each become a small `INotificationProvider` implementation. Not building specific ones into this plan now — the point is the extensibility point exists from day one so adding one later (per a future ask) is a new provider class, not a redesign.

`INotificationDispatcher` (in `VideoForensics.Hosting`) is called from the same sites that write the security audit log, resolves every enabled `INotificationProvider`, and fans the event out to each. `/settings/notifications`: per-provider configuration (SMTP settings, API keys, etc.), per-provider enable/disable, per-event-type urgent/not-urgent toggle.

### 5.7 Auth hardening: rate limiting & step-up re-authentication

Two protective measures, distinct from §5.5/§5.6 which only *observe and report* — these actually block/gate:

- **Rate limiting on auth + pairing endpoints**: ASP.NET Core's built-in rate-limiting middleware (`Microsoft.AspNetCore.RateLimiting`), a fixed/sliding-window limiter keyed by source IP, applied to `/pair`, the WebAuthn authentication ceremony endpoints, and the fallback-key auth endpoint. Past a configurable threshold (default: something like 5 failures / 15 minutes), the source is temporarily locked out (429 responses) rather than allowed to keep guessing. Every lockout is itself an `AuthFailure`-adjacent `SecurityAuditLogEntry` (§5.5) and, past the threshold, urgent by default (§5.6) — reusing the existing audit/notification machinery rather than a separate alerting path.
  - **Caught in review: "source IP" must mean the real client IP, not Cloudflare's edge IP.** Traffic arriving via the Internet tier's tunnel (§5.3) all originates from Cloudflare's own connecting IP unless the app explicitly reads the `CF-Connecting-IP` header — without that, every internet-tier client buckets into one rate-limit key, making the limiter both useless against a real attacker (who blends in with everyone else behind the tunnel) and a hazard to legitimate users (one attacker could exhaust the shared bucket and lock everyone out). The rate-limiting key resolution must check for `CF-Connecting-IP` when present (only trusting it when the connection genuinely came through the configured tunnel) and fall back to the direct connection's remote IP for Local/Network-tier traffic.
  - **Also applied to resource-intensive/provider-facing endpoints, not just auth**: `/api/downloads/*` (§4) is rate-limited too, at a separate, more generous threshold — a compromised or malfunctioning *already-paired* device shouldn't be able to hammer the download-trigger endpoint into a self-inflicted denial-of-service or into tripping Ring's own account-level rate limits.
- **Step-up re-authentication for high-risk actions**: Factory Reset, Device Revocation (§5.4), widening the network tier (Local→Network→Internet, §5.2), and **releasing a Legal Hold** (§4.4 — placing a hold is protective and low-risk, but releasing one is the data-loss-risk half of that action, so it gets the same treatment as the other high-risk actions here) require a **fresh** passkey assertion (or fallback-key re-confirmation) at the moment of the action — a valid existing session alone isn't sufficient. A small `IStepUpAuthChallenge` check runs before those specific action handlers, prompting a new WebAuthn ceremony inline (same UX pattern browsers already show for "confirm it's you" on sensitive operations) even though the user is already signed in.

### 5.8 Health-check endpoint & liveness monitoring

- **`GET /healthz`** (ASP.NET Core's built-in `Microsoft.Extensions.Diagnostics.HealthChecks` middleware) — deliberately **unauthenticated** (so third-party uptime monitors like Uptime Kuma can poll it without needing pairing credentials) and deliberately **minimal**: a bare Healthy/Unhealthy status only, no diagnostic detail (device counts, DB state, etc.) that an unauthenticated caller shouldn't see. Reachability of this endpoint follows whichever network tier (§5.2) is active — a monitor outside the LAN needs the Internet tier (tunnel) active, or the monitor itself needs to run on the same network.
- **Client-side liveness check**: MAUI (and the Web app's own dashboard, for the "am I actually talking to a live backend" case) polls `/healthz` on an interval; if it fails for a configurable window, the client raises its own local notification ("Can't reach the VideoForensics server") — necessarily client-side, since a fully-down server obviously can't notify about its own downtime, unlike §5.6's security events which fire *from* a server that's still up. This is what actually completes "server liveness monitoring" as an in-app feature, complementing (not replacing) an external tool like Uptime Kuma hitting the same `/healthz` endpoint.

### 5.9 Local app-lock (device biometric gate)

Distinct from and *in addition to* §5.1's pairing/passkey auth: §5.1 governs whether a device can talk to the server's API at all; this governs whether **whoever is physically holding an already-paired device** can see anything in the app UI. Picking up an unlocked, already-paired laptop shouldn't be enough to browse the evidence.

- `VideoForensics.MauiApp` requires a successful local biometric/PIN check — Windows Hello, via the `Windows.Security.Credentials.UI.UserConsentVerifier` WinRT API — before showing any app content, on cold launch and again after a configurable idle timeout following backgrounding (`/settings/app-lock`: "lock after immediately / 1 min / 5 min / 15 min in background"). Falls back to the OS's own PIN/password prompt if biometrics aren't enrolled — standard Windows Hello behavior, not a custom fallback to build.
- Implemented via a small `ILocalAuthGate` abstraction rather than calling the WinRT API directly from UI code, deliberately choosing a cross-platform-capable approach (e.g. the `Plugin.Fingerprint.Maui` community package, which also covers Face ID/Touch ID) even though only Windows is in scope now (§ decisions) — so adding iOS/Android later reuses this gate instead of redesigning it.
- **Synergy with step-up auth (§5.7)**: on MAUI specifically, a fresh local Windows Hello unlock can satisfy a step-up re-auth requirement directly, since it's the same underlying mechanism the passkey ceremony already uses on that platform — avoiding a redundant second prompt where the two would otherwise overlap.
- **Web client**: browsers have no equivalent "lock the open tab behind biometrics" pattern. The existing per-session passkey sign-in (§5.1) is the closest equivalent there; a short session-idle-timeout forcing re-authentication is a reasonable complement, flagged as an open UX decision for M6 rather than fully specified here.

### 5.10 Role-based access control (RBAC)

§5.1 answers "is this device allowed to talk to the API at all"; this answers "what is it allowed to do once it can." Four roles, assigned **per Operator** (§5.11 — corrected here in review: an earlier draft of this section said "per paired device," written before the Operator concept existed; a role belongs to the *person*, and travels with them across every device they pair, not to a device in isolation):

- **Read-only**: view everything — evidence, reports, jamming analysis, chain-of-custody, browse events, device config — no mutations of any kind.
- **Review**: Read-only, plus can create annotations — record a manual jamming incident (`JammingToolsOrchestrator.RecordJammingIncidentAsync`), mark evidence as reviewed/flagged. Cannot delete, export, or reconfigure anything.
- **Admin**: Review, plus evidence lifecycle actions — trigger downloads/collection, Export Evidence, Validate Evidence (integrity/reconcile), place *and* release Legal Hold (§4.4 — though releasing one still needs step-up re-auth per §5.7 regardless of role), and day-to-day Configuration (retention days, download/query paths, concurrency, logging, redaction level, report-generation toggles).
- **Super Admin**: Admin, plus everything that changes the server's own trust/security posture or is otherwise irreversible — Add/Revoke paired devices (§5.1/§5.4) and change their roles, Network tier changes (§5.2), Cloudflare Tunnel setup (§5.3), Key Storage Configuration, Media Storage location (§4.2), Manage (Ring) Accounts add/remove, and Factory Reset.

Enforced server-side via ASP.NET Core policy-based authorization (`[Authorize(Policy = "Admin")]`-style, keyed off a role claim on the session, resolved from the Operator, not the device) on every Minimal API endpoint group — never just hidden in the UI, since a hidden-but-reachable endpoint is not actually restricted.

**Bootstrapping**: the very first Operator ever paired to a fresh server has no existing Super Admin to grant them a role, so they implicitly become Super Admin — the "owner." Every subsequent pairing has its Operator's role chosen explicitly by an existing **Super Admin** (matching §7's route table and §5.10's own role list above, which place "Add/Revoke paired devices... and change their roles" under Super Admin, not Admin — corrected here in review from an earlier draft that said "Admin-or-above") via the same "Add Client" flow (§5.1), and a Super Admin can change any Operator's role later — itself a step-up-gated action (§5.7), since granting Super Admin is exactly as sensitive as the actions Super Admin unlocks.

**Super Admin actions require physical presence at the server — enforced via the network tier, not just the role claim.** Even an already-paired, already-authenticated Super Admin device cannot perform Super Admin-gated actions over the Network or Internet tier — those endpoints additionally check that the request arrived via the **Local** tier specifically (loopback — reusing §5.2's existing tier definition exactly, not a new concept), regardless of which tiers happen to be enabled for everything else. A stolen device, a phished tunnel session, or a compromised passkey therefore cannot escalate to revoking other devices, changing storage/tunnel configuration, or factory-resetting the server unless the attacker is physically at the machine — deliberately narrowing the blast radius of any remote credential compromise to Admin-level actions at most. Practical consequence, stated plainly: if the owner only ever accesses their server remotely, Super Admin actions wait until they're next physically at it (or connected via the server's own local network on the same machine — e.g. a MAUI install running *on* the server box counts as Local, since this is a network-path check, not an app-identity check).

**Reconciled against §5.2's LAN-pairing flow, so this isn't self-contradictory**: mDNS discovery and pairing over the Network tier (§5.2) still work exactly as designed — the local-presence check applies to the **initiating/approving** side of a Super Admin action, not to every party involved. "Add Client" (§5.1) already *is* initiated at the server's own screen (step 1: "on the server, the owner opens 'Add Client'"), which is inherently a local action regardless of which tier the *new* device subsequently connects through to complete pairing — a phone pairing in from across the house over the Network tier is fine, because the Super Admin approving that pairing is, by construction, physically at the server generating the QR code. Same logic for Revoke: clicking "Revoke" happens at the server locally; it doesn't matter what tier the device-being-revoked normally uses.

### 5.11 Operator identity & management (legal attribution)

RBAC (§5.10) alone answers "what is this paired identity allowed to do"; it doesn't answer "which specific *person* did this," which matters for legal/chain-of-custody purposes on a shared device — a family laptop might have two people using it, and "Device #3 exported this evidence" is a weaker record than "Jane Doe exported this evidence, from Device #3, at 14:32."

**New `Operator` entity** (Id, DisplayName, CreatedAtUtc, Active flag) — deliberately distinct from the existing Ring-scoped `User` entity (`ProviderUserKey`-keyed, represents the Ring account holder) — represents a local person operating this VideoForensics installation. A paired identity (§5.1) is really the tuple **(Operator, device credential, Role)**, not just a device: one physical device can host multiple Operators (e.g. two Windows Hello profiles on one shared laptop each pairing separately, per §5.1 step 5's "who is this for" step), each with their own passkey and their own role.

**Every attribution point carries `OperatorId`, not just `DeviceId`**: `SecurityAuditLogEntry` (§5.5) and evidence chain-of-custody entries (§4.4's Legal Hold place/release, and more broadly every existing `ActionLog` write this plan's new screens produce) are updated to record who, specifically, performed the action — not just which device the request arrived from.

**`/settings/operators` (Super Admin + Local)**: list Operators, their paired devices/roles, create a new Operator record in advance of them ever connecting (so a Super Admin can pre-provision someone and hand them a pairing QR tied to that record), and **deactivate an Operator** — a bulk action distinct from single-device revocation (§5.4): deactivating an Operator immediately revokes *every* paired-identity credential associated with them, across all their devices, in one action (the right tool for "this person should no longer have any access," vs. §5.4's "this specific device shouldn't," which are different real-world situations).

**Per-session re-verification, not just per-action step-up (§5.7)**: a long-lived session token must not let a session silently carry over between different people on a shared device. A **session**, on MAUI, is one app process lifetime — cold launch already requires this via §5.9's app-lock (that's what satisfies this requirement there; the configurable *idle-timeout* re-lock within the same still-running process is a separate, local-only UI gate — it re-checks Windows Hello to keep showing content, but doesn't tear down and re-establish the server session or produce a new `SessionVerified` entry, since the same Operator's session token is still the one in use throughout; only a fresh cold launch does).

On the Web client, a session is **a genuinely new browser tab/window, not every circuit reconnect** — **caught in review**: an earlier draft defined it as "one browser circuit," but ASP.NET Core Blazor Server circuits reconnect after ordinary transient network blips (a brief WiFi drop, a laptop waking from sleep), and treating every such reconnect as "a new session requiring a fresh WebAuthn prompt" would be disruptive (constant re-prompting during normal use) and could trip §5.7's auth-ceremony rate limiter through nothing but ordinary flaky-network churn. Distinguished instead via a client-side marker (e.g. `sessionStorage`, which persists across a circuit reconnect within the same tab but not across a genuinely new tab/window or a closed-and-reopened tab): if the marker says this tab already completed verification, a circuit reconnect resumes without re-prompting; a fresh tab/window with no marker requires the full ceremony, symmetric with MAUI's cold-launch behavior.

Step-up re-authentication (§5.7) remains layered on top of this for specific high-risk actions even *within* an already-verified session — the two are complementary, not redundant: session-start verification answers "who is this," step-up answers "is it still really them, right now, for this one dangerous thing." **Every session-start verification is itself recorded** as a `SessionVerified` entry in the security audit log (§5.5) — OperatorId, DeviceId, timestamp — regardless of whether anything else notable happened in that session, so there's a positive, queryable record of identity verification to point to, not just an absence-of-failure inference.

### 5.12 Provider API budget protection & DoS detection

**The threat this addresses is specific and worse than generic abuse**: exhausting Ring's own account-level API rate limit doesn't just slow the app down — it blinds `DeviceHealthSyncService` (§3) and therefore jamming detection at exactly the moment an attacker might most want that. A coordinated attack — physically jamming a camera's signal *while* flooding the Ring API (through our own endpoints, or directly against Ring using leaked credentials) to knock out the account's API access — would prevent VideoForensics from ever recording that the jamming happened. This is a different resource than §5.7 protects: §5.7's rate limiting guards *our own* inbound endpoints from being hammered by a bad client; this guards the *outbound* budget to Ring's API, which is shared across every server-tier host and finite in a way we don't control.

- **Self-imposed budget, conservative and shared across hosts**: a new `IProviderApiBudgetGuard` in `VideoForensics.Hosting`, backed by a rolling counter of recent Ring API calls, enforces a ceiling deliberately well below Ring's actual limit — every Ring-calling code path (downloads, Query API, `DeviceHealthSyncService`) checks in with it first and backs off before *we* become the reason the account gets locked out. Given §3's already-noted limitation that console/MCP/`VideoForensics.WebApp` can each independently poll Ring, this budget must be tracked in the shared database (a lightweight rolling-window table), not per-process memory, so multiple concurrently-running hosts don't each think they have the full budget to themselves.
- **Reuse, not reinvent, existing rate-limit detection**: `RingMediaDownloadService.IsRateLimitError(Exception)` (confirmed present in the existing code, `src/providers/ring/provider/Services/RingMediaDownloadService.cs:1319`) already detects Ring's own 429/rate-limit responses — this is the exact signal to escalate, not a new detector to build. Every time it fires, in *any* Ring-calling path, it's logged as a new `SecurityAuditLogEntry` event type `ProviderRateLimitHit` and treated as **urgent by default** (§5.6) — not buried as a routine warning, since "Ring just rejected us" is precisely the "your monitoring may currently be blind" event the whole notification pipeline exists for.
- **Anomalous-volume detection, independent of whether Ring has rejected anything yet**: if the *rate* of Ring-API-triggering requests (downloads, Query API calls, health-sync ticks) spikes abnormally within a short window — even before hitting the self-imposed budget or a real 429 — that's itself suspicious and worth an audit-logged, urgency-classified event (`ProviderApiVolumeAnomaly`), giving an earlier warning than waiting for an actual lockout.
- **Explicit data-gap awareness, not silent false reassurance**: when Ring access is degraded or budget-throttled, `DeviceHealthSyncService`/`JammingToolsOrchestrator` must surface a "no fresh telemetry available" state explicitly in the Jamming Analysis screen and Signal Anomalies report — not silently report "0 incidents," which reads identically to "confirmed clear" rather than "we don't know." This matches the DV-safety framing already established in this codebase's own `JAMMING_ANALYSIS_GUIDE.md` (avoid false reassurance, not just false alarm) — a data gap during a possible attack window is exactly the case that guidance already warns about, just not yet connected to a concrete failure mode until now.
- **Basic network-layer DDoS against the server itself** is substantially already covered elsewhere and not re-designed here: §5.7's rate limiting protects the server's own endpoints from a bad client, and Internet-tier traffic gets Cloudflare's own upstream DDoS mitigation at the tunnel edge (§5.3) as a side benefit of that architecture choice — worth stating explicitly since it's a real, un-costed benefit of the Cloudflare Tunnel decision, not something this plan has to build separately.

## 6. Live progress reporting & urgent-event push (server-executed, one real-time channel)

`IVideoDownloadService`'s polling contract (`GetProgress()`/`GetCurrentDevice()`/`DrainActivityLog()`/`GetPreScanCounts()`) stays as-is on the server side — shared with the MCP server and console, no reason to redesign it there. The RCL's `DownloadProgressPanel.razor` depends on a small abstraction, `IDownloadStatusSource` (`GetProgress()`/`GetCurrentDevice()`/`DrainActivityLog()`/`GetPreScanCounts()`, same shape), rather than `IVideoDownloadService` directly, so the same component works on both hosts:
- On `VideoForensics.WebApp`, `IDownloadStatusSource` is a thin **in-process** wrapper directly calling the real `IVideoDownloadService` (no network hop — it's the server, per §4); its own Blazor Server circuit already handles UI refresh through normal `StateHasChanged` calls when the wrapper's tick fires, no separate real-time infrastructure needed for the server's own UI.
- On `VideoForensics.MauiApp`, `IDownloadStatusSource` is backed by a **SignalR connection** (`/hubs/live`) to the server, not HTTP polling — **caught in review**: an earlier draft of this plan had MAUI polling `GET /api/downloads/status` every ~500ms over plain HTTP while §5.6 separately floated SignalR as an alternative for urgent-event delivery; those were two competing real-time mechanisms for the same underlying need. Consolidated into **one hub** serving both: the server pushes progress ticks *and* urgent security events (§5.6) down the same connection, and MAUI's `DownloadProgressPanel`/toast-notification code both subscribe to it. Falls back to a slower HTTP poll only if the SignalR connection itself is down (matches the liveness-check story in §5.8).

The RCL component itself reacts to `IDownloadStatusSource` updates (a tick on the server's in-process wrapper, a hub message on MAUI) and calls `InvokeAsync(StateHasChanged)` — the component code is identical either way; only how `IDownloadStatusSource` receives its updates differs per host. "Start download" (the button click) goes through the equivalent split: `IDownloadTrigger.StartVideoDownloadAsync(...)` in-process on the server, HTTP `POST /api/downloads/videos` from MAUI (a one-shot command, not something that needs the push channel). Reused for both Download Videos and Download Snapshots screens.

## 10. Execution & dispatch strategy

This plan is large enough that it's meant to be worked milestone-by-milestone, likely by dispatching implementation tasks to a fast/cheap model (Haiku) by default, escalating to a stronger model (Sonnet) when a task turns out to need more judgment than expected.

**Restructure this document into per-milestone files** (not done in this plan-mode pass — plan mode restricts edits to this one file; this is the first action item once implementation starts): split into a short always-loaded overview (Context, Target architecture, the four-layers callout, §1's hosting split) plus one self-contained file per milestone (`m1-foundation.md` … `m8-multi-server.md`), each carrying only the sections relevant to that milestone plus its slice of the route table, decisions, and verification steps. A dispatched task for, say, M2 should only need to load `m2-collection.md`, not the full ~420-line document — most of M2's work (screens over already-existing service calls) is exactly the kind of well-specified, mechanical task a cheaper model handles fine without the rest of this plan's security-design context in front of it.

**Default to Haiku for**: routine CRUD screens, route wiring, DTO/repository mapping, straightforward Razor components over already-existing service calls — the bulk of M1–M5 and M6's non-security screens (Notifications UI, Operator list UI, etc.). These are well-specified enough in §7's route table that a smaller model shouldn't need to infer intent.

**Escalate to Sonnet for** anything where getting it subtly wrong has real security consequences — concretely, the handful of spots already caught needing correction *during this planning session's own review passes* are exactly the list, since that's direct evidence they're easy to get wrong even with a plan in hand:
- The WebAuthn registration/authentication ceremony itself (§5.1) — challenge handling, attestation verification, replay protection are easy to implement in a way that *looks* right and isn't.
- `CF-Connecting-IP` trust boundary (§5.7) — must only be trusted when the immediate connection genuinely came from Cloudflare's edge, never taken at face value from an arbitrary client-supplied header (a naive implementation that trusts the header unconditionally reintroduces exact IP spoofing, defeating the whole point of the fix):
  ```
  ⚠ escalate to Sonnet
  clientIp = IF request.RemoteIpAddress is in Cloudflare's published IP ranges
             AND request has "CF-Connecting-IP" header
             THEN header value
             ELSE request.RemoteIpAddress   // never trust the header from a non-Cloudflare peer
  ```
- SQLCipher bootstrap key ordering (§4.1) — the key (and which provider produced it) must be read from the local bootstrap store *before* `DbContextFactory` ever opens the file; a subtle reordering that reads any part of this from an `IAppSettingRepository` call first silently reintroduces the exact circularity already caught and fixed:
  ```
  ⚠ escalate to Sonnet
  key = LocalBootstrapStore.ReadDbEncryptionKey()   // never IAppSettingRepository here
  dbContextOptions.UseSqlite(connectionString, key)  // key must exist before this line runs
  // only AFTER the DB is open may key-storage *configuration* (which provider, UI toggles)
  // be read from IAppSettingRepository like a normal setting
  ```
- RBAC policy composition, specifically the Super-Admin-**+Local** combination (§5.10) — it's easy to correctly gate on role and forget the additional local-tier check on a subset of endpoints, or to implement the local-tier check only in client-side UI (which doesn't actually restrict anything):
  ```
  ⚠ escalate to Sonnet
  [Authorize(Policy = "SuperAdmin")]
  [RequireLocalTier]   // separate, explicit check — NOT satisfied by role alone,
                        // NOT satisfied by hiding the button in the UI
  ```
- Revocation forcibly disconnecting live SignalR connections (§5.4/§6), not just invalidating the token — easy to implement only the token-invalidation half and consider it done, since that half alone passes a naive "is the old token rejected" test.
- Keeping session-start verification (§5.11) and step-up re-auth (§5.7) as two genuinely separate checks rather than collapsing them into one — a plausible-looking simplification that would quietly weaken the step-up guarantee for actions performed early in a session.
- Provider API budget guard (§5.12) — two easy-to-miss subtleties: the budget counter must be shared (DB-backed) across every server-tier host, not per-process (a per-process implementation looks correct in single-host testing and silently fails to protect anything once a second host is running); and a data gap from a throttled/rate-limited health-sync must render as an explicit "no fresh telemetry" state, never silently fall through to the same UI as a genuine "0 incidents found" result — those two states must never look the same to a viewer.

Anything not on this list defaults to Haiku; anything Haiku produces that doesn't match this plan's stated behavior (or that Haiku itself flags as uncertain) escalates to Sonnet rather than being guessed through.

## Decisions already made (from user answers this session)

- Console app **archived**, not deleted, once M4 reaches parity.
- Web host needs **true concurrent multi-Ring-account** sessions (§2), not single-slot.
- RSSI background sync runs in **all four hosts**, config-toggle to disable, **battery-aware on MAUI**.
- MAUI targets **Windows only** for the initial delivery.
- Server owns the **database and media files**; MAUI supports **offline-local + sync-when-online** (§4/M7).
- Client pairing is **QR-code based, server shows/client scans**, provisioning **passkey auth** (with a stated SecureStorage-key fallback if native WebAuthn on MAUI Windows proves infeasible short-term).
- Three network tiers — **Local / Network(LAN) / Internet(tunnel)** — **Local-only by default**, each wider tier an explicit opt-in.
- Internet exposure via **Cloudflare Tunnel specifically**, with an **in-app GUI** to set it up.
- **Database encrypted at rest** (SQLCipher, reusing the existing key-storage-provider abstraction); **media files explicitly not encrypted**, with a persistent in-app warning instead.
- **Device revocation** is a first-class action alongside pairing, invalidating a device's access immediately (not on natural token expiry).
- A **dedicated security audit log** (separate from the evidence chain-of-custody trail) records pairing, auth, network-tier, tunnel, and revocation events.
- **Only the server pulls new media from any provider.** Clients (MAUI, and the Web app's own UI, uniformly) request downloads/imports via the download-orchestration API; execution always happens server-side. No client host registers provider services or holds provider credentials — MAUI has no code path capable of calling a provider directly, by construction (§1, §6).
- **All providers, not just Ring.** Server-side registration follows the repo's existing provider-agnostic `Contracts/` convention (§1, §3) — Ring today, Wyze per its existing scaffold, any future provider added the same documented way, never hardcoded to one vendor.
- **Urgent security notifications** on events like auth failure, via **email as the reliable baseline plus native push** (Web Push for the browser client, MAUI toast notifications while the app is running) — delivery channels are **pluggable providers** (§5.6) so free push-relay services (e.g. ntfy.sh, Pushover) or SMS gateways can be added later as opt-in options without redesigning the notification layer.
- Backup/disaster-recovery of the centralized evidence store was considered and **explicitly deferred** — not part of this plan; worth revisiting given the server becomes the sole copy of the evidence.
- **Multi-server sync and secure network media storage are explicitly future work, planned now** (§4.2, §4.3, M8): running the server on multiple machines (Windows and/or Linux) with a designated master instance for conflict resolution, plus an optional secure network-storage backend for media — reusing M7's sync engine and §5.1's pairing mechanism rather than inventing new machinery, and relying on OS-level network mounts rather than the app implementing SMB/NFS itself. The `IMediaStorageProvider` seam for this is built in M5, so M8 is additive.
- **Auth hardening**: rate limiting/temporary lockout on auth and pairing endpoints (not just logging failures), and **step-up re-authentication** (a fresh passkey assertion, not just an open session) required for Factory Reset, Device Revocation, and widening the network tier (§5.7).
- **Health-check endpoint** (`GET /healthz`, unauthenticated, minimal-detail) for third-party uptime monitors (e.g. Uptime Kuma), plus a **client-side liveness check** that alerts the owner directly if the server becomes unreachable — distinct from §5.6's security-event notifications, which require the server to still be up to fire (§5.8).
- **Local app-lock on MAUI** (Windows Hello / biometric-or-PIN, via `ILocalAuthGate`) gates the app itself on launch and after an idle timeout — separate from and in addition to §5.1's server-pairing auth, so physical access to an already-paired, already-signed-in device isn't enough on its own (§5.9).
- **Legal hold** lets specific evidence be marked exempt from the retention-policy auto-deletion, logged to the existing evidence chain-of-custody trail (not the new security audit log) since it's evidence-handling, not server security (§4.4). Stealth/quick-hide mode was considered and **not** added to this plan.
- **Role-based access control**, four tiers — Read-only, Review, Admin, Super Admin — assigned **per Operator** (§5.11), enforced server-side on every endpoint (§5.10). The first-ever paired Operator implicitly becomes Super Admin (bootstrapping). **Super Admin actions additionally require the request to arrive via the Local tier** (physical presence at the server), regardless of role or which tiers are otherwise enabled — reusing §5.2's existing tier definition rather than a new mechanism, and reconciled so LAN-based pairing (§5.2's mDNS flow) still works, since the local-presence check applies to the *initiating/approving* side of a Super Admin action, not to every device involved.
- **A new `Operator` entity gives per-person legal attribution**, distinct from the existing Ring-scoped `User` entity — a paired identity is (Operator, device credential, Role), not just a device, so a shared laptop can host multiple separately-attributed people. Every audit/chain-of-custody entry now carries `OperatorId`, not just `DeviceId`. `/settings/operators` (Super Admin + Local) manages Operator records and supports deactivating a person entirely (revoking all their devices at once), distinct from single-device revocation (§5.4). **Every session (MAUI process lifetime / new Web browser circuit) requires a fresh WebAuthn ceremony at start** — no silently-resumed long-lived tokens — explicitly re-confirming which Operator is present, and every such verification is itself logged (`SessionVerified`, §5.5) as a positive record, not just an absence of failure (§5.11).
- **Provider API budget protection & DoS detection** (§5.12): a self-imposed, cross-host-shared ceiling on Ring API call volume so *we're* never the reason the account gets rate-limited, escalating both Ring's own rate-limit rejections (reusing the existing `IsRateLimitError` detection already in `RingMediaDownloadService`) and abnormal call-volume spikes as urgent security events. Motivated by a specific threat: an attacker could flood the Ring API to blind jamming detection at the same moment they're physically jamming a camera's signal. Jamming/signal-anomaly screens explicitly show a "no fresh telemetry" data-gap state rather than silently reporting "0 incidents" when this happens, consistent with this codebase's existing DV-safety guidance against false reassurance.

### Architecture review findings (self-review pass, applied)

A dedicated review of the plan-as-drafted, prompted by the user, surfaced and fixed:
- **Contradiction**: `DeviceHealthSyncService` was specified to run on all four hosts including MAUI, directly violating the "MAUI never calls a provider API" rule established later in the same plan (§1 vs. original §3). Fixed: server-tier hosts only (§3).
- **Cloudflare Tunnel breaks naive IP-based rate limiting** unless `CF-Connecting-IP` is explicitly read — otherwise every internet-tier client shares one bucket. Fixed (§5.7).
- **SQLCipher key bootstrap circularity**: the key-storage-provider selection can't live inside the DB it's meant to unlock. Fixed: DB key lives in the same local bootstrap store already used for credentials, outside the encrypted DB (§4.1).
- **New secrets had no stated home** (SMTP, notification-provider API keys, Cloudflare credentials, network-storage credentials) — now explicitly routed through the existing key-storage-provider abstraction, not new plaintext settings (§4.1).
- **Cert pinning was stated but not explicitly enforced on every connection** — fixed to be explicit, plus a mismatch is now itself a logged security event (§5.1).
- **Two competing real-time mechanisms** (§6's HTTP polling vs. §5.6's floated SignalR) consolidated into one SignalR hub serving both download progress and urgent-event push (§6).
- **Rate limiting scope was auth-only** — extended to `/api/downloads/*` so a compromised paired device can't DoS the server or trip Ring's own rate limits (§5.7).
- **Legal Hold had no step-up requirement** — releasing a hold (the data-loss-risk half of that feature) now requires the same fresh re-authentication as Factory Reset/Device Revocation (§5.7/§4.4).

**Second pass** (after Operator identity/§5.11 was added, which left some earlier sections stale):
- **Stale contradiction**: §5.10's own text still said roles were "assigned per paired device" and chosen "by an existing Admin-or-above," written before §5.11 existed — contradicted both §5.11 and the route table (which already correctly said "per Operator" / Super-Admin-only). Fixed (§5.10).
- **Revocation didn't account for live connections**: invalidating a session token doesn't sever an already-open, persistent SignalR connection (§6) — only blocks future discrete requests. Revocation now explicitly force-disconnects the hub connection too (§5.4).
- **"New session" was defined too literally for the Web client**: "one browser circuit" would treat ordinary transient reconnects (a brief WiFi drop) as requiring a full re-prompt, which is disruptive and risks tripping the auth rate limiter through normal flaky-network use, not an attack. Refined to "a genuinely new tab/window," tracked via a client-side marker that survives a same-tab reconnect (§5.11).
- **MAUI's idle-timeout re-lock vs. cold-launch session-start weren't clearly distinguished**: the idle-timeout re-lock (§5.9) is a local-only UI gate within the same still-running session, not a new `SessionVerified` event — only cold launch starts a new session. Clarified (§5.11).
- **Query API's server-execution pattern wasn't explicit in the route table** — could read as MAUI calling providers directly, contradicting §1. Clarified (§7).
