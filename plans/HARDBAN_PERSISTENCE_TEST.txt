Requirement Analysis:
=============================================================

Current Implementation (HttpUtility.cs):
- Hard-ban state persisted to disk: ring_hard_ban.txt
- File location: %ProgramData%\VideoForensics\ring_hard_ban.txt
- Storage format: Single long value (DateTime.Ticks as string)
- Load timing: EnsureHardBanStateLoaded() called on first check
- Static field: _hardBanUntilUtc (in-memory cache of persisted value)

Problem Solved by Persistence:
- User closes app during hard-ban
- App relaunches within ban window
- Without persistence: New process has no memory of ban
- Result: Fresh attempts to contact Ring repeat the violation
- Without fix: Account stays banned for hours due to repeated probes

Current Hard-Ban Mechanics:
=============================================================

Escalation Path:
1. First 429: Set throttle cooldown to 30s (wait, then retry)
2. Second 429: Increase to max 5m cooldown
3. Third consecutive 429: Trigger hard-ban (1 hour)
4. Hard-ban persisted to disk
5. All subsequent requests fail immediately (no network call)

Methods Involved:
- GetHardBanUntilUtc(): Check if hard-ban active
- RecordThrottled(): Record a 429, escalate to hard-ban if needed
- OverrideHardBan(): User requests override (let them try once more)
- PersistHardBanState(): Write current state to disk
- EnsureHardBanStateLoaded(): Load persisted state on startup

Test Scenario:
=============================================================

Three-Part Simulation:

PART 1: Establish Hard-Ban State
Steps:
1. Create HttpUtility instance
2. Simulate receiving 429 response (RecordThrottled)
3. Repeat for 3 consecutive throttles to trigger hard-ban
4. Verify _hardBanUntilUtc is set
5. Verify ring_hard_ban.txt written to disk with future timestamp
6. Verify GetHardBanUntilUtc() returns non-null value

Expected Result:
- _hardBanUntilUtc = DateTime.UtcNow + TimeSpan.FromHours(1)
- File exists with valid Ticks format
- GetHardBanUntilUtc() returns same value

PART 2: Simulate Process Restart
Steps:
1. Create NEW HttpUtility instance (simulates fresh process)
2. Internal state reset (static fields NOT yet loaded)
3. Call GetHardBanUntilUtc() to trigger EnsureHardBanStateLoaded()
4. Verify file is read from disk
5. Verify _hardBanUntilUtc populated from file
6. Verify returned value matches persisted value

Expected Result:
- EnsureHardBanStateLoaded() reads ring_hard_ban.txt
- _hardBanUntilUtc matches previous process's value
- GetHardBanUntilUtc() returns non-null (ban still active)
- Time remaining: Still ~1 hour (or time elapsed if test adds delay)

PART 3: Verify HTTP Requests Blocked Until Ban Expires
Steps:
1. Attempt to make HTTP request while hard-ban active
2. Verify request fails immediately (GetContents throws or returns error)
3. Verify NO network call made (critical - should fail fast)
4. Wait until ban expires (or simulate expiration)
5. Attempt HTTP request again
6. Verify request succeeds (or gets proper error, not hard-ban block)

Expected Result:
- Request blocked while ban active
- No HTTP calls made during hard-ban
- Request succeeds after ban expires
- Performance: Fast fail (<1ms) vs. network timeout

Challenges & Solutions:
=============================================================

CHALLENGE 1: Static Field Pollution Across Tests
- HttpUtility uses static fields shared across all instances
- Multiple tests will interfere with each other's state
- Solution: Use test isolation class, reset statics before/after
- Or: Create dedicated test double with non-static ban state

CHALLENGE 2: Simulating Process Restart
- Hard to restart process within unit test
- Static fields don't reset on new class instance
- Solution: Use reflection to reset statics OR create test double
- Better solution: Use IKeyStorageProvider pattern (make ban state injectable)

CHALLENGE 3: Time-Based Testing
- Hard-ban expires after 1 hour
- Can't actually wait 1 hour in test
- Solution: Mock SystemClock OR refactor to use injectable IClock
- Alternatively: Create test that verifies logic, not actual time passage

CHALLENGE 4: File System Access
- Tests need to write to ProgramData
- Permissions issues on some CI agents
- Solution: Use Path.GetTempPath() for testing, not actual ProgramData
- Or: Mock file system access via abstraction

Recommended Refactoring (Phase 2):
=============================================================

TO MAKE THIS TESTABLE:

1. Extract Ban State to Separate Interface:
   ```csharp
   public interface IBanStateProvider
   {
       DateTime? GetHardBanUntilUtc();
       void RecordBan(DateTime expiryUtc);
       void ClearBan();
   }
   ```

2. Make HttpUtility Accept Injected IBanStateProvider:
   ```csharp
   public HttpUtility(IBanStateProvider banStateProvider, ...)
   {
       _banState = banStateProvider;
   }
   ```

3. Create Test Implementation of IBanStateProvider:
   ```csharp
   public class TestBanStateProvider : IBanStateProvider
   {
       public DateTime? _banUntilUtc { get; set; }
       // Implements interface with simple in-memory storage
   }
   ```

4. Test becomes straightforward:
   ```csharp
   [Fact]
   public void HardBan_RestoresAfterRestart()
   {
       var banState = new TestBanStateProvider();
       var utility = new HttpUtility(banState, ...);

       // Simulate hard-ban
       banState._banUntilUtc = DateTime.UtcNow.AddHours(1);

       // Verify requests blocked
       Assert.Throws<HttpRequestException>(() => utility.GetContents(...));
   }
   ```
